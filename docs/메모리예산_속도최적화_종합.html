24GB 통합 메모리 맥에서 로컬 LLM PDF 추출 속도의 모든 병목이 메모리 예산에서 비롯됨을 하나의 관점으로 종합하고, 메모리를 비우는 레버(모델 교체, num_ctx 하향, FLASH_ATTENTION+KV캐시 q8_0 양자화, keep_alive)와 메모리를 늘려 OOM을 유발하는 병렬화를 구분하며, 정확도 위험별로 분류한 인터랙티브 문서

메모리 예산 관점 — 속도 최적화 종합

병렬화가 왜 안 되는가 + 그럼 무엇을 해야 하는가 — 하나의 그림으로
하나의 원인, 하나의 규칙

지금 겪는 모든 것 — 배치당 343초, 스왑, 병렬화 실패 — 은 24GB 메모리 예산 하나로 설명됩니다. 30b는 혼자서도 예산을 꽉 채워 스왑(느림)이 걸립니다. 그래서 규칙은 단순합니다: 메모리를 비우는 레버 = 해결, 메모리를 늘리는 병렬화 = 악화(OOM).

짚고 가기 — num_ctx 32768 → 16384

랩에 나오는 num_ctx 레버가 왜 무위험으로 속도를 주는지.
num_ctx가 뭔가
모델이 한 번에 다룰 수 있는 최대 토큰(글자 조각) 수 = 문맥 창의 크기. 32768 토큰이면 대략 A4 수십 장 분량입니다. 이 창을 채우려고 잡는 임시 메모리가 KV 캐시이고, 창이 클수록 KV도 커집니다.
왜 줄여도 안전한가
현재 코드는 배치마다 보고서를 최대 12,000자(≈6천 토큰)까지만 잘라 넣습니다. 32768은 실제 쓰는 양의 5배 넘는 빈 방을 예약해 둔 셈. 16384로 줄여도 6천 토큰 청크는 다 들어가므로 모델이 보는 내용·출력 품질은 그대로입니다.
왜 빨라지나
KV 캐시가 반으로 줄어 되찾은 메모리로 스왑이 풀립니다. 24GB에서 30b + 32768은 예산을 넘겨(랩에서 확인) 스왑 → 343초/배치의 원인. 16384로 낮추면 예산 안에 들어와 정확도 손실 0으로 속도만 얻습니다. 가중치(모델)를 건드리는 양자화·모델교체와 달리 출력에 전혀 영향이 없어 무위험으로 분류한 이유입니다. FLASH+q8와 함께 쓰면 KV가 한 번 더 줄어 효과가 겹칩니다.

정확도 우선 권장 순서

1 · 지금 (무위험)
30b 유지 + num_ctx 16384 + FLASH_ATTENTION + KV q8_0 + keep_alive. KV 캐시가 줄어 스왑이 풀리고 정확도는 그대로. 랩에서 30b+32768이 OOM이던 게 이 조합으로 예산 안에 들어옵니다.
2 · 더 빨라야 하면 (측정)
골든셋으로 14b → 8b 정답율 비교. 통과 시 채택 — 완전 GPU 상주라 5~10배가 결정적. 배치 축소는 그 다음, 따로.
✕ 하지 말 것
병렬화. 단일 24GB에선 메모리를 배로 요구해 OOM만 유발하고 처리량은 그대로. 진짜 병렬은 장비 증설이 전제.

무위험 조합 적용 (환경변수 + 인자)

# Ollama 서버 환경변수 — KV 캐시 절반, 모델은 30b 그대로
export OLLAMA_FLASH_ATTENTION=1
export OLLAMA_KV_CACHE_TYPE=q8_0        # q8_0=고품질, 거의 무손실 (q4는 더 공격적)
ollama serve

# 추출 호출 — num_ctx만 낮춰도 KV가 더 줄어듦
extract_from_pdf(raw, model, num_ctx=16384, keep_alive="30m")
종합 한 줄
속도 문제는 곧 메모리 문제입니다. 메모리를 비우면(KV 양자화·num_ctx·모델 축소) 빨라지고, 늘리면(병렬화) OOM. 정확도 우선이면 먼저 무위험(FLASH+q8·num_ctx)으로 30b 스왑을 풀고, 부족하면 골든셋 검증 후 14b/8b로 내려가세요.
