정확도를 속도보다 우선하는 관점에서, qwen3:30b-a3b가 구조화 추출에 반드시 더 정확하지 않은 이유(MoE 3B 활성 vs 7b dense, 24GB 스왑)와 5→3배치의 정확도 위험을 설명하고, 개선 레버를 정확도 무위험(num_ctx·keep_alive·CLI)과 측정 필요(모델·배치)로 분류해 안전한 타협 경로와 골든셋 검증법을 제시하고, 레버·CLI·num_ctx 용어를 설명하는 인터랙티브 문서

정확도 우선 관점 — 개선안 재평가

속도보다 정확도가 중요할 때, 어디까지 타협 가능한가
오해 1 — "30b라서 더 정확하다"
qwen3:30b-a3b는 MoE — 토큰당 활성 파라미터 ≈ 3B. 구조화 추출에서 qwen2.5:7b(7B 전량 활성 dense)보다 반드시 정확하다는 보장이 없습니다. 게다가 24GB에서 30b + num_ctx 32768은 스왑이 걸릴 수 있어 — 343초/배치의 진짜 원인이 '정확도용 연산'이 아니라 '메모리 한계'일 가능성이 큽니다.
오해 2 — "39/43이 정확도다"
39/43은 '채움율'(빈칸 아님)이지 '정답율'이 아닙니다. 작은 모델이 43칸을 다 채우고도 값이 틀릴 수 있어요. 정확도로 의사결정하려면 정답이 붙은 골든셋에서 값 단위 일치율을 봐야 합니다.
결론부터 — 타협 가능한 시나리오는 "레버 분리"

개선 레버는 정확도에 영향이 전혀 없는 것과 정확도를 바꿀 수 있는 것으로 갈립니다. 무위험 레버만 먼저 적용하면 지금의 5배치·30b 정확도를 그대로 유지한 채 속도만 얻습니다. 모델·배치는 골든셋으로 정확도를 확인한 뒤에만 손대세요.

먼저 — 용어 3가지

아래 분류기를 보기 전에 알아두면 좋은 개념입니다.
레버(lever) — 결과를 바꾸는 조절 손잡이
원래 뜻은 "지렛대". 여기선 건드리면 속도·정확도가 크게 움직이는 조정 항목을 비유한 말입니다. "모델 크기", "배치 수", "num_ctx"가 각각 하나의 레버죠. 지렛대처럼 작게 조정해도 결과가 크게 바뀌고, 여러 개를 동시에 당기면 효과가 섞여 원인 파악이 어려워집니다. 그래서 "레버를 분리해 하나씩 당기자"고 하는 겁니다.
CLI — 터미널에서 실행하는 방식
Command Line Interface(명령줄 인터페이스)의 약자. 마우스로 클릭하는 화면(GUI) 대신 터미널에 명령어를 타이핑해 프로그램을 실행하는 방식입니다. 지금은 Streamlit 웹 화면에서 버튼으로 돌리는데, "CLI로 분리"는 그 배치 작업을 화면에서 떼어 python batch_ingest.py ./reports처럼 독립 프로그램으로 실행한다는 뜻입니다. 8시간 작업이 브라우저 세션에 묶이지 않아 탭을 닫거나 새로고침해도 안 끊깁니다. 추출 로직은 그대로, 실행 껍데기만 바뀌므로 정확도 영향 0.
num_ctx 32768 → 16384 — 문맥 창 크기 줄이기
num_ctx는 모델이 한 번에 다룰 수 있는 최대 토큰(글자 조각) 수 = 문맥 창의 크기입니다. 32768 토큰이면 대략 A4 수십 장 분량.

왜 줄여도 안전한가 — 현재 코드는 배치마다 보고서를 최대 12,000자(≈6천 토큰)까지만 잘라 넣습니다. 창을 32768로 열어둔 건 실제 쓰는 양의 5배가 넘는 빈 방을 예약해 둔 셈. 16384로 줄여도 6천 토큰 청크는 여유 있게 다 들어가므로 모델이 보는 내용은 하나도 안 잘리고 출력 품질도 그대로입니다.

왜 속도가 빨라지나 — 창이 클수록 KV 캐시(임시 메모리)가 커집니다. 24GB 맥에서 30b 모델까지 올리면 이 캐시가 메모리를 압박해 스왑(느린 디스크로 밀려남)이 생길 수 있고, 배치당 343초가 이 때문일 가능성이 큽니다. 16384로 낮추면 메모리를 되찾아 스왑이 풀리므로, 정확도는 그대로인데 속도만 빨라지는 대표적 무위험 레버가 됩니다.

권장 — 정확도 우선 2단계

STEP 1 · 지금 바로 (무위험)
30b · 5배치 그대로 유지 + num_ctx 16384 + keep_alive + CLI 분리. 정확도 손실 0. 스왑이 원인이었다면 속도가 눈에 띄게 개선됩니다. 이것만으로도 실사용 가능한지 먼저 확인.
STEP 2 · 더 빨라야 할 때만 (측정)
골든셋으로 모델 하나씩(30b→8b→7b) 정확도 비교. 통과하면 채택. 배치는 마지막에 따로 5→4→3 검증. 한 번에 둘을 바꾸지 않기.

결정 도구 — 골든셋 정확도 검증

"채움율"이 아니라 "정답율"로 판단하기 위한 최소 절차.
# eval_extraction.py — 설정별 값 단위 정답율 비교
# 1) 대표 보고서 10건을 사람이 직접 43필드 라벨링 → golden.json
# 2) 각 설정으로 추출 후 필드별 일치 여부 집계
CONFIGS = [
    ("30b·5배치", "qwen3:30b-a3b", BATCHES),      # 기준(baseline)
    ("7b·5배치",  "qwen2.5:7b-instruct", BATCHES),
    ("7b·3배치",  "qwen2.5:7b-instruct", BATCHES_3),
]
for name, model, batches in CONFIGS:
    hit = total = 0
    for pdf, truth in golden.items():
        pred,_ = extract_from_pdf(open(pdf,'rb').read(), model, batches=batches)
        for k, v in truth.items():
            total += 1
            hit   += norm(pred.get(k)) == norm(v)     # 정규화 후 값 일치
    print(f"{name}: 정답율 {hit/total:.1%}")         # 채움율 아님 — 정답율
# → 30b 대비 정답율이 허용범위(예: -2%p 이내)면 그 설정 채택
한 줄 답
추천안은 통째로는 정확도 타협이지만, 무위험 레버(num_ctx·keep_alive·CLI)만 떼어 쓰면 정확도 타협 없이 속도를 얻습니다. 모델·배치 축소는 골든셋 정답율이 허용범위일 때만 — 그게 '타협 가능한' 유일한 방식입니다.
