## 1. 시스템 개요

### 이 시스템은 무엇인가요?

철도사고 조사보고서(PDF 파일)를 업로드하면, AI가 보고서를 읽고 사고의 핵심 정보를 자동으로 정리해주는 프로그램입니다.

사람이 직접 보고서를 읽고 표에 입력하던 작업을 AI가 대신하며, 사고의 위험도를 자동으로 계산하고 담당자에게 알림을 보내는 기능까지 포함합니다.

### 주요 기능 한눈에 보기

| 기능 | 설명 |
|------|------|
| **보고서 자동 분석** | PDF 업로드 → 43개 항목 자동 추출 (발생일자, 원인, 피해현황 등) |
| **위험도 자동 계산** | 사망자·부상자·피해액·지연시간을 수식에 대입해 0~100점 산정 |
| **등급 분류** | Critical / High / Medium / Low 4단계 자동 분류 |
| **알림 발송** | 등급별로 이메일·슬랙·문자 자동 발송 |
| **AI 에이전트** | 자연어 질문으로 데이터 조회·분석 가능 |
| **대시보드** | 누적 사고 데이터 통계·추이 시각화 |

## 2. 시스템 구성 (비전공자용 설명)

### 시스템의 3개 층

```
┌─────────────────────────────────────────────┐
│  화면 층 (사용자가 보는 부분)                    │
│  - 웹 브라우저에서 실행되는 화면                  │
│  - 파일 업로드, 결과 확인, 그래프 보기             │
└────────────────┬────────────────────────────┘
                 │ 화면이 요청
┌────────────────▼────────────────────────────┐
│  처리 층 (두뇌 역할)                           │
│  - PDF에서 텍스트 추출                          │
│  - AI(LLM)에게 분석 요청                       │
│  - 위험도 점수 계산                             │
└────────────────┬────────────────────────────┘
                 │ 데이터 저장/읽기
┌────────────────▼────────────────────────────┐
│  데이터 층 (저장소)                             │
│  - 사고 데이터베이스 (DuckDB)                   │
│  - 알림 설정 파일 (JSON)                        │
└─────────────────────────────────────────────┘
```

> **왜 3개 층으로 나눴나요?**  
> 화면 코드와 처리 코드가 섞이면 수정할 때 부작용이 생깁니다. 층을 나누면 화면만 바꾸거나 처리 로직만 바꿀 수 있어 유지보수가 쉬워집니다.

### 주요 파일 역할

```
Safety_agent/
├── safety_analytics.py   ← 웹 화면 (브라우저에서 보이는 모든 것)
├── safety_core.py        ← 핵심 처리 로직 (PDF 분석, 위험도 계산)
├── shared/
│   ├── railway_accidents.duckdb  ← 사고 데이터 저장소
│   └── notify_config.json        ← 알림 수신자·규칙 설정
└── railway_agent/
    ├── railway_safety_agent.py   ← AI 자율 에이전트
    └── agent_ui.py               ← 에이전트 화면
```

## 3. PDF 자동 추출 파이프라인

### "파이프라인"이란?

물이 수도관을 따라 순서대로 흐르듯, PDF 보고서가 여러 처리 단계를 거쳐 최종 데이터가 되는 과정입니다.

### 현재 추출 흐름 (v1.7.2 기준)

```
PDF 파일 업로드
      │
      ▼
[1단계] PDF → 텍스트 변환
  pymupdf4llm 라이브러리가 PDF의 모든 글자를
  컴퓨터가 읽을 수 있는 텍스트로 변환 (최대 28,000자)
      │
      ▼
[2단계] 정규식 기본 추출
  패턴 인식으로 날짜·시간·기관명·사망/부상자수·열차종류를
  형식 기반으로 즉시 추출
  (예: "2025년 3월 23일" → "2025-03-23")
      │
      ▼
[3단계] AI(LLM) 5배치 순차 추출  ← 핵심 단계
  보고서 전체(28,000자)를 AI에게 5번에 나눠 보내
  43개 항목을 그룹별로 추출
  (배치4: 고장·조치·개요 전용 한국어 강조 지시문 포함)
      │
      ▼
[4단계] 고장 4개 필드 전용 재추출 (조건부)
  고장부품명·고장현상·고장원인·조치내용이 여전히
  비어있을 경우, 키워드 기반 안내와 함께 전체 보고서로 재시도
  ('고장','이상','불량','파손','결함','조치','복구','교체' 키워드 활용)
      │
      ▼
[5단계] 이벤트개요 전용 요약 생성 (조건부)
  이벤트개요가 비어있을 경우, 이미 추출된 기본 정보
  (발생일자·노선·원인·피해 등)를 힌트로 함께 제공하며
  AI에게 한국어 3~5문장 요약을 직접 작성하도록 요청
      │
      ▼
[6단계] 이벤트개요 합성 fallback (조건부)
  5단계도 실패할 경우, 이미 추출된 필드들을
  조합해 기본 문장 자동 생성
  (예: "2025-03-23 경부선 노선에서 탈선가 발생하였습니다.")
      │
      ▼
[7단계] 마무리 처리
  - 데이터출처 기본값 설정 ('PDF 자동 추출')
  - 추출률 계산 및 표시 (43개 중 몇 개 추출됐는지)
      │
      ▼
최종 결과: 43개 항목 채워진 데이터 + 추출률 리포트
```

### 배치(Batch)란?

AI에게 한 번에 43개 항목을 모두 물어보면 답변이 부정확해질 수 있습니다.
그래서 항목을 5개 그룹으로 나눠 차례로 물어봅니다.
**모든 배치가 보고서 전체(28,000자)를 읽습니다.**

| 배치 | 담당 항목 | 항목 수 | 특이사항 |
|------|----------|---------|---------|
| 배치1 | 발생일시·기관·노선·이벤트분류·주원인 | 9개 | — |
| 배치2 | 근본원인·직접원인·운행영향·지연 정보 | 9개 | — |
| 배치3 | 피해현황·위치(역명·행정구역) | 8개 | — |
| 배치4 | 위치상세·기상환경 | 8개 | — |
| 배치5 | 선로·신호·고장부품·조치내용·개요 | 9개 | **한국어 강조 지시문 포함** |

> 배치5에는 "고장부품명/고장현상/고장원인/조치내용은 보고서 전체에서 반드시 찾으세요" 라는  
> 별도 지시문이 한국어로 포함되어 AI의 집중도를 높입니다.

## 4. 위험도 산정 방식

### 점수 계산 공식

```
위험도 점수 = 인명피해 점수 + 재산피해 점수 + 지연 점수 + 이벤트 보정

인명피해 점수 = min((사망자 + 부상자÷100) × 20,  최대 40점)
재산피해 점수 = min(피해액(백만원) ÷ 50,         최대 20점)
지연 점수     = min(최대지연시간(분) ÷ 40,        최대 15점)
이벤트 보정   = 탈선·충돌·화재·폭발·추락·붕괴 → +15점
               사고류 → +10점 / 장애류 → +5점
```

### 강제 등급 상향 (안전망)

계산 결과와 무관하게 피해 규모가 심각하면 강제로 등급을 높입니다.

| 조건 | 최저 보장 점수 | 최저 등급 |
|------|-------------|---------|
| 사망자 1명 이상 | 60점 | High |
| 사망 3명 이상 또는 부상 20명 이상 | 80점 | Critical |
| 사망 5명 이상 | 90점 | Critical |

### 위험 등급

| 등급 | 점수 범위 | 의미 |
|------|---------|------|
| **Critical** | 80~100점 | 즉각 대응 필요 |
| **High** | 60~79점 | 신속 대응 필요 |
| **Medium** | 25~59점 | 주의 관찰 |
| **Low** | 0~24점 | 일반 관리 |

## 5. AI 모델 선택 가이드

### 사용 가능한 모델

이 시스템은 인터넷 없이 내 컴퓨터에서 직접 실행되는 AI(로컬 LLM)를 사용합니다.

| 모델 | 크기 | RAM 사용 | 추출률 | 속도 | 권장 용도 |
|------|-----|---------|--------|------|---------|
| **qwen3:30b-a3b** ⭐ | 30B (MoE) | ~19GB | 95%+ | 빠름 | **기본값 · 24GB RAM 최적** |
| **qwen3:32b** | 32B | ~20GB | 95%+ | 느림 | RAM 여유 있을 때 |
| **qwen3:8b** | 8B | ~5GB | 중간 | 매우 빠름 | 빠른 테스트용 |
| **qwen2.5:7b-instruct** | 7B | ~5GB | 79% | 빠름 | 경량 처리 |
| **llama3.1:8b** | 8B | ~5GB | 미검증 | 중간 | — |

### qwen3:30b-a3b가 기본값인 이유 (MoE 구조)

> **MoE(Mixture of Experts)란?**  
> 30B(300억)개의 파라미터를 갖고 있지만, 실제 추론(계산)할 때는 그 중 일부(약 3B)만 활성화됩니다.  
> 마치 100명의 전문가 팀이 있는데, 질문에 따라 가장 적합한 전문가 10명만 투입하는 방식입니다.
>
> **결과**: qwen3:32b와 비슷한 품질을 유지하면서 처리 속도는 2~3배 빠르고, 메모리 압박이 적습니다.

| | qwen3:32b | qwen3:30b-a3b |
|--|-----------|---------------|
| 총 파라미터 | 32B | 30B |
| 실제 활성 파라미터 | 32B (전체) | ~3B (일부) |
| RAM 사용량 | ~20GB | ~19GB |
| 추론 속도 | 기준 | **2~3배 빠름** |
| 한국어 품질 | 95%+ | 95%+ |
| 24GB RAM 적합성 | 경계선 (스왑 발생 가능) | **적합** |

### v1.7.0 : 모델명 오타 수정 (2026년 5월) ← **가장 치명적 버그**

**문제**: 코드에 모델명이 `qwen3:32`로 잘못 입력되어 있었습니다.  
실제 설치된 모델명은 `qwen3:32b`였습니다.  
이 한 글자 차이(`b` 누락)로 AI가 "모델 없음 오류"를 발생시켰고,  
이 오류가 조용히 무시되어 AI 없이 정규식만으로 추출이 진행되었습니다.

**비유**: 전화번호 한 자리를 틀리게 입력해서 항상 연결이 안 됐는데,  
전화기(시스템)는 "연결 실패"를 표시하지 않고 그냥 혼자 메모를 남긴 상황과 같습니다.

**수정 결과**:

| | 수정 전 | 수정 후 |
|--|--------|--------|
| qwen3:32b 추출률 | ~47% (AI 미작동) | **95% 이상** |
| qwen2.5:7b-instruct | 79% | 79% (변동 없음) |

### v1.6.0 : 프롬프트 전면 개선 (2026년 5월)

**문제**: AI에게 보내는 질문(프롬프트)이 영어로 작성되어 있어서,  
한국어 보고서의 항목명과 매핑이 부정확했습니다.  
또한 `format="json"` 옵션이 AI가 한국어 텍스트를 생성하는 것을 내부적으로 막고 있었습니다.

**비유**:  
- 영어로 "find the cause" → 한국어 보고서에서 "원인"을 못 찾는 것
- `format="json"` = AI에게 "영어 알파벳만 써라" 라고 제약을 건 것과 같음

**해결**:
- 모든 AI 지시문을 한국어로 재작성
- `format="json"` 제약 완전 제거
- 이벤트개요 전용 '요약 생성' 단계 추가 (단순 추출이 아닌 생성 태스크로 전환)

### v1.4.0 : qwen3 모델 설정 오류 수정 (2026년 5월)

**문제**: qwen3 모델 사용 시 내부적으로 '생각하는 시간'이 너무 길어  
결과를 출력하기 전에 허용된 출력량(2048 토큰)이 소진되어 JSON이 잘렸습니다.

**비유**: 시험지 답안을 작성하다가 종이가 모자라 답이 중간에 잘린 것과 같습니다.

**해결**:
- 출력 허용량 2048 → 4096 토큰으로 2배 확대
- `reasoning=False` 파라미터로 불필요한 '생각 과정' 출력 완전 차단

| **DuckDB** | 데이터베이스 | 파일 캐비닛 (데이터 보관) |
| **pymupdf4llm** | PDF → 텍스트 변환 | PDF 번역기 |

## 8. 오류 대응 구조

### AI가 실패해도 결과가 나오는 이유

이 시스템은 AI 오류에 대비해 다단계 안전망을 갖추고 있습니다.

```
1순위: AI(LLM) 5배치 추출
      → 각 배치 실패 시 1회 자동 재시도

2순위: 고장 4개 필드 전용 재추출
      → 키워드 안내 포함 보완 시도

3순위: 이벤트개요 LLM 요약 생성
      → 기추출 정보를 힌트로 제공, 2회 시도

4순위: 이벤트개요 합성 생성
      → LLM 전체 실패 시 추출된 필드로 문장 자동 조합

5순위: 정규식(패턴 매칭) 추출
      → 날짜·숫자·기관명 등 형식이 고정된 항목은 항상 추출
```

### 모델 오류 시 사용자 안내

모델명이 잘못되거나 Ollama 서버가 꺼져 있을 때 화면에 안내 메시지를 표시합니다.

```
❌ 모델 'qwen3:30b-a3b' 을 찾을 수 없습니다. Ollama에서 모델명을 확인하세요.
```
