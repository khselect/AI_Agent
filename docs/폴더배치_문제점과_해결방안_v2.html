지금 구조 — Streamlit 메인 스레드에서 8시간 블로킹
폴더 루프를 그대로 탭 안에 넣으면 아래 4곳에서 터집니다.
# tab_input.py — 폴더 지정 (문제 있는 버전)
folder = st.text_input("보고서 폴더 경로")
files  = glob.glob(f"{folder}/*.pdf")            ①
for f in files:                                ②
    data, _ = extract_from_pdf(open(f,'rb').read(), model)  # 10분
    insert_accident(data, f)                     ③
    st.progress(i/len(files))                     ④
① 중복·순서 없음
glob 순서 임의, 같은 파일 재적재 무방비
② 세션 블로킹
8시간 동기 루프 → UI 정지, 탭 끊기면 전멸
③ 재개 불가
40번째서 죽으면 처음부터 다시
④ 진행상태 휘발
rerun/새로고침 시 카운터 소실
권장 구조 — 별도 CLI + 체크포인트 (1번 권장방향 A~D)
배치 루프를 Streamlit에서 떼어 batch_ingest.py로. UI는 상태만 폴링.
# batch_ingest.py — python batch_ingest.py ./reports
import hashlib, os, sys, glob, duckdb

files = glob.glob(f"{sys.argv[1]}/*.pdf")
files.sort(key=lambda f: os.stat(f).st_mtime)   A

done = load_registry()                            B
for i, f in enumerate(files):
    raw  = open(f,'rb').read()
    h    = hashlib.sha256(raw).hexdigest()        D2
    if h in done: continue              # 이미 적재 → 스킵

    data, _ = extract_from_pdf(raw, model)        C1 # 직렬 1건씩
    insert_accident(data, f, file_hash=h)         C2 # 파일단위 커밋
    record_registry(h, f)                         B
    write_status(i+1, len(files), f)              # status.json ← UI 폴링
A · 직렬 유지 + mtime 정렬
Ollama가 어차피 요청을 직렬 처리 — 병렬화하면 VRAM OOM만 유발. 순서는 st_mtime으로(결과엔 무영향).
B · 적재 레지스트리 → 재개·멱등
처리 완료분을 기록. 재실행 시 새 파일만. 40번째서 죽어도 39건 보존 후 이어서.
C · 파일단위 즉시 커밋 + 세션 분리
한 건 끝날 때마다 DuckDB 커밋. 8시간 작업을 웹 세션이 아닌 CLI 프로세스에 둠. Streamlit은 status.json만 폴링해 진행률 표시.
D · 파일당 시간 단축 (가장 효과 큼)
배치 5→3, 짧은 보고서는 num_ctx↓, 작은/양자화 모델·GPU. 10분→2~3분이면 50건을 1~2시간에.
2번 — 생성시간으로는 중복을 못 막습니다
복붙하면 10개 파일의 생성시간이 전부 같아질 수 있어 판별 불가. 내용 해시가 정답.
생성시간 기준
복사/이동 시 타임스탬프 리셋·동일화. 파일명 달라도 같은 내용이면 못 걸러냄.
SHA-256 해시 기준
file_hash UNIQUE 컬럼 + 레지스트리. 내용이 같으면 파일명·시간 무관하게 확실히 배제. 의미상 순서는 추출된 발생일자로.

부록 — SHA-256 해시란?

아무리 크고 긴 데이터든 고정된 길이의 "지문"으로 바꿔주는 함수입니다.

파일 하나를 넣으면 항상 256비트, 즉 64자리 16진수 문자열 하나가 나옵니다. 내용이 조금만 달라져도 지문 전체가 완전히 바뀝니다.

"철도사고보고서.pdf"의 내용 전체
        │  SHA-256
        ▼
9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08

# "2건 사망" → "3건 사망" 으로 한 글자만 고치면
        ▼
e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855  # 완전히 다른 값
결정적
같은 내용이면 항상 같은 값. 파일명·생성시간이 달라도 내용이 동일하면 지문이 똑같습니다.
눈사태 효과
단 1비트만 달라도 결과 전체가 뒤바뀝니다. 미세한 변경도 확실히 감지.
일방향
해시값에서 원본을 복원할 수 없습니다. 원래는 비밀번호 저장·위변조 검증용 보안 함수.
충돌 저항성
서로 다른 두 파일이 같은 해시일 확률은 사실상 0(2256). "해시가 같다 = 내용이 같다"고 안심하고 판단.

그래서 앞의 설계에서는 파일을 읽어 hashlib.sha256(raw).hexdigest()로 지문을 뽑고, 그 지문이 DB에 이미 있으면 "이미 처리한 파일"로 보고 건너뜁니다. 생성시간과 달리 복사·이름변경에 흔들리지 않는 이유가 이것입니다.

한 가지 구분할 점
이건 바이트 단위로 완전히 동일한 파일만 같다고 봅니다. 같은 사고를 다룬 다른 PDF(스캔본 vs 워드 출력본)는 내용이 비슷해도 바이트가 달라 해시가 다릅니다. 그런 "의미상 중복"까지 잡으려면 발생일자+노선+이벤트소분류 같은 소프트 키로 별도 검토하는 단계가 필요합니다.
